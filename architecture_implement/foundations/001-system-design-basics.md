# System Design Basics

## Зачем этот файл

Перед паттернами нужно договориться о базовых сущностях. Большинство system design задач сводятся к одному вопросу:

> Как принять запрос пользователя, обработать его, сохранить или прочитать данные и выдержать рост нагрузки?

Паттерны вроде [[consistent-hashing]], [[outbox]] или [[saga]] появляются позже. Сначала важно понимать, из каких деталей вообще собирается система.

## Базовая схема

```
Client -> API -> Service -> Database
```

- **Client** — браузер, мобильное приложение, другой сервис.
- **API** — входная точка: HTTP/gRPC endpoint, gateway, load balancer.
- **Service** — бизнес-логика: создать заказ, получить URL, отправить сообщение.
- **Database** — durable storage: данные должны пережить рестарт сервиса.

На маленьком масштабе этого часто достаточно.

## Что добавляется при росте

```
Client -> Load Balancer -> API Services -> Cache -> Database
                                      -> Queue -> Workers
```

- **Load Balancer** распределяет запросы между несколькими API-инстансами.
- **Cache** ускоряет чтение и снижает нагрузку на БД.
- **Queue / Broker** разрывает синхронную цепочку: работа может быть сделана позже worker'ом.
- **Worker** выполняет фоновые задачи: отправка email, пересчёт рейтинга, обработка видео.
- **Replica** — копия данных или сервиса для отказоустойчивости и масштабирования чтения.
- **Shard / Partition** — часть данных, выделенная по ключу.

## Node, Cluster, Shard, Replica

- **Node** — один сервер или процесс, который выполняет часть работы.
- **Cluster** — группа нод, работающих как единая система.
- **Shard** — горизонтальный кусок данных. Например, пользователи `0..999999` на shard A, остальные на shard B.
- **Partition** — близкое понятие: часть данных или лога, часто внутри брокеров и storage-систем.
- **Replica** — копия данных для чтения или отказоустойчивости.

Shard отвечает на вопрос:

> Где лежат эти данные?

Replica отвечает на вопрос:

> Есть ли копия, если основная нода умерла или перегружена?

## Key

Во многих системах всё начинается с ключа:

```
user_id
order_id
short_url_code
message_id
file_hash
```

Ключ нужен, чтобы:
- найти запись;
- выбрать shard;
- выбрать cache node;
- сохранить порядок событий;
- дедуплицировать запрос.

Когда в архитектуре появляется несколько нод, вопрос "какой ключ куда идёт" становится центральным.

## Stateful и Stateless

**Stateless service** не хранит важное состояние между запросами.

```
Request 1 -> API-1
Request 2 -> API-3
```

Такой сервис легко масштабировать через load balancer.

**Stateful service** держит состояние.

```
user:123 connection lives on websocket-node-7
match:55 lives on game-server-2
```

Тут уже нельзя отправлять запросы случайно: нужно стабильное routing-правило.

## Минимальный словарь перед паттернами

- **Latency** — сколько времени занимает запрос.
- **Throughput** — сколько запросов система обрабатывает в секунду.
- **Durability** — данные не теряются после записи.
- **Availability** — система отвечает даже при отказах.
- **Consistency** — разные части системы видят согласованное состояние.
- **Bottleneck** — компонент, который первым перестаёт выдерживать нагрузку.
