# Idempotency Key

## What

Клиент передаёт серверу уникальный ключ для конкретной операции. Сервер хранит результат первого выполнения и при повторном запросе с тем же ключом возвращает сохранённый результат, не выполняя операцию повторно.

## Why / Problem it solves

В распределённых системах клиент часто не знает, дошёл ли его запрос:
- Сеть упала между запросом и ответом.
- Таймаут на клиенте, хотя сервер обработал.
- Ретраи на любом уровне (клиент, прокси, gateway).

Без дедупликации клиент при ретрае создаст **второй заказ / второй платёж / второго пользователя**. Idempotency Key переносит ответственность за уникальность на клиента (он генерирует ключ), а сервер просто соблюдает контракт «один ключ — один результат».

## When to apply

**Применять:**
- Любая mutating-операция через ненадёжную сеть (HTTP POST для оплаты, заказа, регистрации).
- Consumer кафки / SQS, где гарантия at-least-once → возможны дубли (см. [[outbox]]).

**Не применять (без нужды):**
- GET-запросы — они уже идемпотентны.
- Операции, у которых дубль безопасен сам по себе (например, "set user status = X" — идемпотентна по природе).

## How

### Механика (HTTP API)

1. Клиент генерирует UUID/ULID для операции.
2. Передаёт в заголовке: `Idempotency-Key: 9a3c...`.
3. Сервер до выполнения операции:
   - Смотрит, есть ли запись по ключу.
   - Если есть и операция завершена → возвращает сохранённый ответ.
   - Если есть и операция в процессе → 409 Conflict или ждёт.
   - Если нет → создаёт запись `(key, status=in_progress)`, выполняет, сохраняет ответ.
4. TTL на запись (24h–7d — зависит от домена).

### Где хранить

- **Redis** — быстро, естественный TTL. Минус: не транзакционен с основной БД.
- **БД (Postgres)** — таблица `idempotency_keys (key, request_hash, response_body, created_at)`. Можно атомарно с бизнес-операцией.
- **Гибрид** — Redis для горячих ключей + БД как источник правды.

### Инварианты

- Ключ + операция должны быть проверены до коммита бизнес-операции.
- При совпадении ключа, но **разном** теле запроса — вернуть ошибку (клиент перепутал ключи).
- TTL должен быть больше любого разумного окна ретраев.

### Диаграмма

```
Client                Server               DB
  │ POST /orders        │                   │
  │ Idempotency-Key:X   │                   │
  ├────────────────────▶│                   │
  │                     │ SELECT key=X      │
  │                     ├──────────────────▶│
  │                     │  not found        │
  │                     │◀──────────────────┤
  │                     │ INSERT (X, in_progress)
  │                     │ ... business ...  │
  │                     │ UPDATE (X, done, response)
  │                     │                   │
  │ 200 OK              │                   │
  │◀────────────────────┤                   │
  │                     │                   │
  │ POST /orders        │ (retry)           │
  │ Idempotency-Key:X   │                   │
  ├────────────────────▶│ SELECT key=X      │
  │                     │   → done          │
  │ 200 OK (cached)     │                   │
  │◀────────────────────┤                   │
```

## Common pitfalls

- **Сравнивать только ключ, не тело.** Если клиент с одним ключом отправил разные тела — это баг клиента, надо вернуть 422, не молча принять.
- **TTL слишком короткий.** Клиент ретраит через 25 часов, запись истекла, операция выполнится дважды.
- **Хранение только в Redis.** Redis упал → потеряли дедупликацию. Для критичных операций (платежи) хранить в БД.
- **In-progress без таймаута.** Сервис упал после INSERT `in_progress`, но до завершения. Запись висит, новые ретраи получают 409 навсегда. Нужен timeout / retry policy.
- **Не атомарно с бизнес-операцией.** Записали ключ, начали бизнес-операцию, упали. Нужно либо в одной TX, либо отдельный механизм очистки protected-by-key.

## Variations

- **Server-generated keys** — сервер сам выдаёт ключ через `POST /idempotency-keys` перед основной операцией. Сложнее, но контроль уникальности на сервере.
- **Natural keys** — использовать естественный уникальный идентификатор (order_number от клиента) вместо отдельного header. Меньше движущихся частей, но клиент должен уметь его сгенерировать.
