# Consistent Hashing простыми словами

Связанный паттерн: [[consistent-hashing]].

## Какая проблема

Есть несколько серверов:

```text
cache-0
cache-1
cache-2
```

И есть много ключей:

```text
user:1
user:2
product:10
order:55
```

Нужно решить:

```text
на какой сервер класть каждый ключ?
```

Если сегодня `user:1` положили на `cache-0`, то завтра запрос за `user:1` тоже должен пойти на `cache-0`. Иначе мы не найдём данные.

## Что обычно делают без consistent hashing

Самый простой способ:

```text
server = hash(key) % number_of_servers
```

Например серверов 3:

```text
hash("user:1") % 3 = 0  -> cache-0
hash("user:2") % 3 = 1  -> cache-1
hash("order:55") % 3 = 2 -> cache-2
```

Пока серверов всегда 3, всё нормально.

## Где ломается простой подход

Проблема начинается, когда добавили новый сервер.

Было 3:

```text
server = hash(key) % 3
```

Стало 4:

```text
server = hash(key) % 4
```

Формула изменилась. Из-за этого почти все ключи получают новое место.

Пример:

```text
было:
hash("user:1") % 3 = 0 -> cache-0

стало:
hash("user:1") % 4 = 2 -> cache-2
```

Сам ключ не изменился. Изменилось только количество серверов.

Главная проблема:

```text
при добавлении или удалении сервера обычный hash(key) % N
массово меняет распределение ключей
```

## Что приходится делать без consistent hashing

Есть два варианта.

### Вариант 1: переложить почти все данные заново

Это называется `rebalance` или `resharding`.

Нужно пройти по всем ключам и пересчитать, где каждый должен лежать по новой формуле.

Пример:

```text
key = user:1

старое место:
hash(user:1) % 3 = node-0

новое место:
hash(user:1) % 4 = node-2
```

Значит ключ нужно перенести:

```text
node-0 -> node-2
```

Так делается для всех ключей:

```text
user:1    node-0 -> node-2
user:2    node-1 -> node-1
order:5   node-2 -> node-3
photo:9   node-0 -> node-0
```

Если новое место отличается от старого, данные копируют на новый узел и потом удаляют со старого.

Простые шаги:

1. Добавили новый узел.
2. Заморозили или ограничили записи.
3. Прошлись по всем ключам.
4. Для каждого ключа посчитали новое место: `hash(key) % 4`.
5. Если ключ теперь должен быть на другом узле, перенесли его.
6. Обновили routing config у приложения.
7. Удалили старые копии.

Проблема: при миллионах или миллиардах ключей это долго, дорого и создаёт большую нагрузку на сеть, диски и сервисы.

### Вариант 2: пережить массовые cache miss

Если это кэш, можно ничего не переносить.

Но приложение уже ищет ключи по новой формуле:

```text
user:1 -> cache-2
```

А старые данные лежат по старой формуле:

```text
user:1 -> cache-0
```

Кэш выглядит почти пустым. Запросы массово идут в базу данных, и кэш постепенно прогревается заново.

Для кэша это иногда допустимо, но опасно: база может получить резкий всплеск нагрузки.

Для storage такой подход обычно не подходит, потому что данные должны реально находиться там, где их ищет routing layer.

## Как помогает consistent hashing

Consistent hashing меняет способ распределения.

Вместо:

```text
hash(key) % N
```

мы представляем hash space как кольцо.

Серверы попадают на это кольцо:

```text
cache-0
cache-1
cache-2
```

Ключи тоже попадают на это кольцо.

Правило:

```text
ключ принадлежит ближайшему серверу по часовой стрелке
```

Когда добавляется новый сервер, он забирает только часть ключей из соседнего диапазона.

То есть:

```text
без consistent hashing:
добавили сервер -> почти все ключи поменяли место

с consistent hashing:
добавили сервер -> поменялась только часть ключей рядом с новым сервером
```

## Главная польза

Consistent hashing нужен не просто чтобы распределить ключи.

Обычный `hash(key) % N` тоже распределяет ключи.

Consistent hashing нужен, чтобы:

```text
при добавлении, удалении или падении узла
не пришлось перераспределять почти все данные
```

## Где это применяется

Типичные места:

- distributed cache;
- CDN / edge cache;
- distributed storage;
- shard routing;
- stateful services;
- worker ownership;
- search index shards.

## Короткая формула

Используй consistent hashing, когда вопрос звучит так:

```text
у меня есть много ключей и несколько нод;
как выбрать ноду для ключа так,
чтобы при изменении числа нод переехало минимум ключей?
```
